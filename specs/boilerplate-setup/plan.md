### Data flow — authenticated request (FR-010, FR-011)

1. User submits `LoginPage` (Formik, validated by a Zod schema) → `supabase.auth.signInWithPassword()`.
2. supabase-js persists the session (localStorage) and emits `onAuthStateChange`; `AuthProvider` exposes `{ session, user, status }` via React context.
3. A page calls `useQuery({ queryKey: ['me'], queryFn: () => apiClient.get('/me') })`.
4. `apiClient` request interceptor calls `supabase.auth.getSession()` (auto-refreshes if the refresh token is valid). If there is no session, or `expires_at` is in the past, it **rejects with `AuthRequiredError` before any network I/O** (FR-011). Otherwise it sets `Authorization: Bearer <access_token>`.
5. API middleware chain runs; `requireAuth` extracts the bearer token and calls `authService.verifyAccessToken(token)` → `supabaseAdmin.auth.getUser(token)` (OQ-001). On success sets `req.user = { id, email, role }`; on missing/invalid token → `AppError(401, 'UNAUTHORIZED')`.
6. Controller calls `userService.getCurrentUser(req.user)` → `sendSuccess(res, { user })` → `{ success: true, data: { user } }`.
7. `apiClient` response interceptor unwraps `data.data` for TanStack Query; errors are normalised to `ApiError { status, code, message }`. A 401 from the server triggers a local `supabase.auth.signOut()` so `RequireAuth` redirects to `/login`.

### Data flow — AI call (FR-012, FR-013, FR-014)

`Orchestrator.run(workflow, input)` → assigns `workflowId` → for each agent: `agent.run(input)` → `BaseAgent` builds prompt → `aiProvider.complete()` (adapter chosen by `AI_PROVIDER`) → raw text → `extractJson()` → `JSON.parse` → `outputSchema.safeParse()` → on failure throw `AIOutputValidationError` (nothing downstream executes); on success return the validated object. If an agent declares `requiresApproval`, the orchestrator stops and returns `{ status: 'awaiting_approval', pending }` instead of executing the next step. Every stage emits a Pino event.

### System boundaries

- **Trust boundary 1 (browser → API):** everything from the browser is untrusted; validated by Zod in `validators/` + `middleware/validate.js`; identity only from `requireAuth`.
- **Trust boundary 2 (LLM → API):** LLM output is untrusted; it must be Zod-validated in `BaseAgent` before it is used.
- **Secret boundary:** `SUPABASE_SERVICE_ROLE_KEY` and `AI_API_KEY` exist only in the API process. The browser bundle gets only `VITE_*` vars, which are public by design (API URL, Supabase URL, anon key).

## API contracts

All routes are under `/api/v1`. Success: `{ "success": true, "data": { … } }`. Error: `{ "success": false, "error": { "code": "<string>", "message": "<string>" } }` — exactly these two fields; no `stack`, no `details` containing internals (ADR-3).

| Method & path | Auth | Success | Errors |
|---|---|---|---|
| `GET /api/v1/health` | public | 200 `{ data: { status: "ok", uptime: <seconds>, timestamp: "<ISO>" } }` | 429 |
| `GET /api/v1/me` | Bearer | 200 `{ data: { user: { id, email } } }` | 401 `UNAUTHORIZED`, 429 |
| any unmatched path (incl. `/health`, `/me` without prefix) | — | — | 404 `NOT_FOUND` (FR-009) |
| any `POST` with body > 1 MB (any path) | — | — | 413 `PAYLOAD_TOO_LARGE` (FR-004) |
| any request with malformed JSON body | — | — | 400 `INVALID_JSON` |

No AI endpoint is exposed in the scaffold: an unauthenticated or even authenticated generic "prompt" route is a cost and abuse vector with no domain purpose. FR-012/013/014 are verified at the module level with mocked SDK clients.

**Middleware order in `createApp()` (order is load-bearing):**

1. `requestLogger` (pino-http) — first, so 413/429/404 are logged too (FR-003).
2. `helmet()` — headers on every response incl. errors.
3. `cors({ origin: config.corsOrigin })` — before the rate limiter so 429s are readable by the browser.
4. `rateLimiter` — `windowMs` 15 min, `limit` 100, `standardHeaders: 'draft-8'`, `legacyHeaders: false`, `handler: (req, res, next) => next(new AppError(429, 'RATE_LIMITED', …))`. Placed before body parsing so floods are not parsed.
5. `express.json({ limit: '1mb' })`.
6. `app.use('/api/v1', v1Router)`.
7. `notFound` → `next(new AppError(404, 'NOT_FOUND', …))`.
8. `errorHandler` — maps: `AppError` → its status/code; `ZodError` → 400 `VALIDATION_ERROR` (message summarises issue paths only); body-parser `type === 'entity.too.large'` → 413; `type === 'entity.parse.failed'` → 400 `INVALID_JSON`; anything else → 500 `INTERNAL_ERROR` with generic message. Logs the full error (with stack) server-side at `error` level for 5xx, `warn` for 4xx. Never echoes `err.message` for 5xx.

**`createApp(deps)` injection points:** `{ config, logger, authService, rateLimit }` with production defaults. Tests inject a fake `authService` (FR-010 without a live Supabase) and may inject a small `rateLimit.max` — though FR-005 is also verified at the real default (101 requests via Supertest is fast).

**Validation pattern:** `validate({ body?, query?, params? })` runs `schema.parse` and stores results on `req.validated` (Express 5 makes `req.query` a getter, so it cannot be reassigned). Controllers read only `req.validated`.

**Controller/service split:** routes only wire `path → [middleware] → controller`. Controllers only translate HTTP ↔ service call ↔ `sendSuccess`. All decisions live in services.

- [x] Plain JavaScript only; no TypeScript, no Turborepo, no ORM (spec out-of-scope).
- [x] `.env.example` lists every variable; `.env`, `.env.local` gitignored.
- [x] All I/O async/await.

## Architecture Decision Records (ADRs)

### ADR-1: Monorepo mechanics — pnpm workspaces with catalog, source-consumed internal packages

- **Problem:** How to wire four workspaces so `pnpm install` is clean (FR-001), internal packages need no build (OQ-004), and shared libraries (zod, vitest, eslint, prettier) never drift between apps.
- **Options considered:** (a) pnpm workspaces + `workspace:*` deps + `exports` pointing at `src/` + a pnpm `catalog:` for shared versions; (b) same, but per-package version ranges without a catalog — simpler file, but web and api can silently resolve different Zod majors; (c) Turborepo/Nx — excluded by spec; (d) TS-style path aliases in Vite/Node — needs duplicate alias config in two toolchains and breaks `pnpm ls` dependency visibility.
- **Chosen solution:** (a). `pnpm-workspace.yaml` lists `apps/*`, `packages/*`, defines `catalog:` entries for zod, vitest, eslint, prettier, react, react-dom, and `allowBuilds: { esbuild: true, supabase: true }`. `@brainx/shared` and `@brainx/ui` have `"exports": { ".": "./src/index.js" }` and are declared as `workspace:*` deps (shared by web + api; ui by web only). Root `package.json` pins `packageManager: pnpm@12.x` for Corepack.
- **Reasoning:** The spec's "pnpm path aliases" is best realised by the workspace protocol — it is what pnpm natively resolves, it shows in `pnpm ls -r`, and both Vite and Node follow the symlink to source with zero config. The catalog costs one extra YAML block but guarantees a single Zod major across the trust boundary. `allowBuilds` is required, not optional: pnpm ≥11 defaults `strictDepBuilds: true`, so an unlisted postinstall (Supabase CLI binary download, esbuild) fails the install with `ERR_PNPM_IGNORED_BUILDS` and would fail FR-001. Accepted tradeoff: `@brainx/ui` can contain JSX and therefore must never be imported by `apps/api` (Node cannot parse JSX); enforced by only declaring it as a web dependency.

### ADR-2: ESM throughout

- **Problem:** CommonJS or ES modules for api, packages, and root config files.
- **Options considered:** (a) ESM everywhere (`"type":"module"`); (b) CommonJS api + ESM web — familiar Express idiom, but shared package must then be dual-format or require a build, violating OQ-004; (c) mixed with `.mjs`/`.cjs` extensions — noisy and error-prone.
- **Chosen solution:** (a) — root, both apps, both packages declare `"type": "module"`; root `eslint.config.js` is ESM.
- **Reasoning:** One source-consumed `@brainx/shared` must be importable by Vite (ESM-only) and Node — only ESM satisfies both without a build. Vitest, Supertest, Express 5, pino, both AI SDKs and supabase-js all support ESM. Accepted tradeoff: no `__dirname` (use `import.meta.dirname`, Node ≥20.11) and some older Express-ecosystem snippets online need translation.

### ADR-3: Error envelope `{ success: false, error: { code, message } }` supersedes playbook `{ error: string }`

- **Problem:** The org constitution check requires `{ error: string }`; project CLAUDE.md and spec (FR-004/005/008/010) require `{ success: false, error: { code, message } }`. These conflict.
- **Options considered:** (a) follow the playbook `{ error: string }` — would fail FR-004/005/008/010 and contradict CLAUDE.md; (b) follow CLAUDE.md/spec and record an exception — keeps an approved spec satisfiable and gives the frontend a machine-readable `code`; (c) emit both (`error` as object plus a top-level `message` string) — ambiguous, and `error` still isn't a string.
- **Chosen solution:** (b). Single `errorHandler` is the only place that writes error bodies; `rateLimiter` and `notFound` route through it via `next(AppError)`.
- **Reasoning:** The approved spec is the contract for this feature and the project CLAUDE.md is the project-level constitution; the playbook template's line is a generic default. `code` lets the frontend branch on errors without parsing messages. Accepted tradeoff: this project diverges from the org default; logged in `notes.md` with a recommendation to update the template.

### ADR-4: Express 5 over Express 4

- **Problem:** Which Express major to scaffold on.
- **Options considered:** (a) Express 5 — current `latest` on npm, forwards rejected promises from async handlers to the error handler natively, removes deprecated APIs; (b) Express 4 — largest body of examples, but needs an `asyncHandler` wrapper or `express-async-errors` patch on every async route, and a forgotten wrapper produces an unhandled rejection instead of an envelope (FR-008 risk).
- **Chosen solution:** Express 5.
- **Reasoning:** Native async error propagation removes a whole class of FR-008 bugs and one dependency. Accepted tradeoffs: new path syntax (no bare `*`; the 404 handler uses `app.use` without a path), `req.query` is a read-only getter (handled by `req.validated`, see API contracts), and some copy-pasted v4 snippets will not work.

### ADR-5: `createApp(deps)` factory in `app.js`, `listen()` in `server.js`

- **Problem:** FR-006 requires `src/app.js`; Supertest needs an app instance without a bound port; FR-010 must be testable without a live Supabase.
- **Options considered:** (a) `app.js` exports a module-level singleton app that also calls `listen()` — simplest, but tests bind ports and cannot swap dependencies; (b) `app.js` exports a singleton without `listen()`, tests use `vi.mock` to replace modules — works, but relies on module-mock ordering and hides dependencies; (c) `app.js` exports `createApp({ config, logger, authService, rateLimit })` with production defaults, and `server.js` does config load + `listen()` + graceful shutdown.
- **Chosen solution:** (c). `package.json` `start` runs `node src/server.js`.
- **Reasoning:** Explicit injection makes tests deterministic (fresh rate-limit store per test, fake auth service) and documents the app's external dependencies. Accepted tradeoff: a small amount of plumbing, and `app.js` is not the process entry point — the spec requires it to exist, not to be the entry, so FR-006 holds.

### ADR-6: Environment configuration — single root env files, dotenv + Zod in api, explicit public `VITE_SUPABASE_*` vars

- **Problem:** The spec wants root-level `.env` / `.env.local` / `.env.example`. The api must load them from `apps/api` cwd; the web app needs Supabase URL and anon key in the browser, but CLAUDE.md lists only `SUPABASE_URL` / `SUPABASE_ANON_KEY` (un-prefixed, invisible to Vite).
- **Options considered:**
  - Loading (api): (i) `node --env-file-if-exists` flags — no dependency, but flags don't apply under Vitest and path handling in scripts differs across shells; (ii) `process.loadEnvFile()` — built-in, but precedence semantics across two files are less explicit; (iii) `dotenv` with explicit root paths — tiny, ubiquitous, same behaviour in server and tests.
  - Exposing Supabase to web: (i) add `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` — standard Vite + Supabase convention, duplicates two values; (ii) `envPrefix` including `SUPABASE_URL`/`SUPABASE_ANON_KEY` — prefix matching is one careless edit (`SUPABASE_`) away from bundling the service-role key; (iii) `define` injection from `loadEnv` — non-standard, surprising; (iv) fetch config from the API at boot — adds a round-trip and a failure mode before login.
- **Chosen solution:** api `config/env.js` loads `<root>/.env.local` then `<root>/.env` with dotenv (no override, so real env > .local > .env), then parses with a Zod schema and exports a frozen `config`; fails fast listing missing variable **names** (never values). Supabase vars are required at boot; AI vars are shape-checked if present and enforced when the provider is first created (`AI_NOT_CONFIGURED`), so the scaffold boots before a team has an AI key. Web: `vite.config.js` sets `envDir: '../..'`; add `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. `vite.config.js` also compares `VITE_SUPABASE_URL` with `SUPABASE_URL` when both are present and throws a clear error on mismatch (added after sparring review — see notes.md). Vitest configs supply placeholder env values for tests.
- **Reasoning:** Explicit `VITE_` names keep Vite's default "only `VITE_` is public" rule intact, which is the strongest guard against leaking the service-role key; the anon key is designed to be public (RLS is the protection). Accepted tradeoffs: two duplicated values (mitigated by the mismatch check) and a CLAUDE.md env-list update, plus one small dependency (dotenv).

### ADR-7: Server-side token verification via `supabase.auth.getUser(jwt)` (confirms OQ-001)

- **Problem:** How `requireAuth` validates Supabase access tokens.
- **Options considered:** (a) `getUser(jwt)` on the service-role client — authoritative, honours revocation/sign-out, one network round-trip to Supabase Auth per protected request; (b) local JWT verification with `jose` against the project JWKS (or `auth.getClaims()`) — no round-trip, but revocation lag until expiry and extra key-rotation handling; (c) shared-secret HS256 verification — legacy, requires distributing the JWT secret to the api.
- **Chosen solution:** (a), as decided in the spec. Wrapped in `authService.verifyAccessToken()` so the strategy can change without touching middleware.
- **Reasoning:** For a hackathon scaffold, correctness and simplicity outweigh the per-request latency (tens of ms locally). Accepted tradeoff: availability of the API's protected routes depends on Supabase Auth; if latency matters later, switch the service implementation to (b) — a change confined to one file.

### ADR-8: Frontend auth state lives in supabase-js + React context, not Redux or TanStack Query; Axios gates unauthenticated calls

- **Problem:** Where the session lives and how FR-011's "blocked at the client" is enforced, given CLAUDE.md's rule that Redux holds client state only.
- **Options considered:** (a) mirror the session in a Redux slice — duplicates supabase-js's own store, risks stale tokens, and a session is arguably server-issued state; (b) TanStack Query `useQuery(['session'])` — caching/refetch semantics fight supabase-js auto-refresh; (c) supabase-js is the single source of truth; a thin `AuthProvider` subscribes to `onAuthStateChange` and exposes `{ session, user, status }`; `apiClient` reads the token at request time via `getSession()`.
- **Chosen solution:** (c). `apiClient` requires auth by default; callers opt out with `{ skipAuth: true }` (used for `/health`). Missing or expired session → `AuthRequiredError` rejected in the request interceptor (no network call). Server 401 → local `signOut()`. `RequireAuth` layout route redirects to `/login` when `status === 'unauthenticated'`.
- **Reasoning:** One owner of the token eliminates drift; reading at request time means refreshed tokens are always used. Secure-by-default gating satisfies FR-011 even if a developer forgets a route guard. Accepted tradeoff: auth state is not visible in Redux DevTools, and public endpoints need an explicit `skipAuth`.

### ADR-9: AI provider layer — official SDKs behind an in-house adapter interface

- **Problem:** FR-012 requires switching Anthropic ↔ OpenAI by env var only; CLAUDE.md requires a provider abstraction and token-usage logging.
- **Options considered:** (a) official `@anthropic-ai/sdk` + `openai` behind a ~50-line adapter each exposing `complete({ system, messages, maxTokens, temperature, jsonSchema? }) → AIProviderResult`; (b) Vercel AI SDK (`ai` + `@ai-sdk/*`) — multi-provider and Zod-aware `generateObject` out of the box, but a meta-framework with frequent breaking majors, and its internal validation would blur the explicit "validate before use" step CLAUDE.md asks for; (c) raw `fetch` to each REST API — no dependencies, but we re-implement retries, streaming, error typing, and track API changes ourselves.
- **Chosen solution:** (a). `integrations/ai/index.js` holds a registry `{ anthropic, openai }`; `createAIProvider(config.ai)` looks up `AI_PROVIDER`, throws `AI_NOT_CONFIGURED` for unknown/missing values, and dynamically imports only the selected SDK. Provider errors are wrapped as `AI_PROVIDER_ERROR` with the upstream message logged, not returned.
- **Reasoning:** Only two providers are required; first-party SDKs expose new features (native structured output, prompt caching) first and are stable. Our own interface keeps swap cost at "add one adapter file", keeps usage mapping explicit for logging, and keeps validation visibly in our code. Accepted tradeoff: adding a third provider costs a new adapter; teams wanting many providers could later implement one adapter over the AI SDK without changing agents.

### ADR-10: AI output validation and orchestration model

- **Problem:** How agents obtain structured JSON and guarantee Zod validation before use (FR-013), and what the orchestrator does (FR-014) without over-building.
- **Options considered:** (a) prompt-instructed JSON, `extractJson` + `JSON.parse` + `schema.safeParse` in `BaseAgent`, no automatic retry; (b) rely on provider-native structured output only — fewer malformed responses, but provider-specific and still not a substitute for our own validation; (c) automatic repair/retry loop — better success rate, hides cost and latency, and is behaviour teams should choose per domain.
- **Chosen solution:** (a) with a hook for (b): `BaseAgent` subclasses declare `name`, `outputSchema` (Zod), `buildPrompt(input)`, optional `requiresApproval`. `BaseAgent.run()` passes `z.toJSONSchema(outputSchema)` as an optional `jsonSchema` hint that adapters may use for native structured output; regardless, the result is always `safeParse`d, and failure throws `AIOutputValidationError` (`AI_OUTPUT_INVALID`) after logging `validation failed`. `maxRetries` option defaults to 0. `Orchestrator.run(steps, input)` runs agents sequentially, generates `workflowId` with `crypto.randomUUID()`, passes each validated output to the next step, and stops with `awaiting_approval` before any step whose agent has `requiresApproval`. No approval persistence (domain-specific, out of scope).
- **Reasoning:** Our Zod parse is the single enforcement point regardless of provider behaviour, which is exactly FR-013. Sequential orchestration is the minimal useful shape; parallelism and tools are added per domain. Accepted tradeoff: more validation failures from weaker models until native structured output is enabled in an adapter.

### ADR-11: Tailwind CSS v4 via `@tailwindcss/vite`

- **Problem:** Tailwind integration method.
- **Options considered:** (a) v4 with the first-party Vite plugin — zero config file, `@import "tailwindcss"` in CSS, CSS-first theming; (b) v3 via PostCSS + `tailwind.config.js` + autoprefixer — more tutorials, three extra files, legacy major.
- **Chosen solution:** (a).
- **Reasoning:** Current major, fewest moving parts, fastest builds. Accepted tradeoff: v3-era snippets (`tailwind.config.js` theme extension, `@tailwind base`) must be translated to v4's `@theme` syntax; `packages/ui` components will need an `@source` directive in `index.css` when populated so their classes are detected.

### ADR-12: React Router v7 in data (library) mode

- **Problem:** Which React Router mode.
- **Options considered:** (a) `react-router` v7 `createBrowserRouter` + `RouterProvider` — plain SPA, works with any Vite setup, loaders available if wanted; (b) v7 framework mode (Vite plugin, file routes, SSR-capable) — more structure but changes the build pipeline and deploy target; (c) declarative `<BrowserRouter><Routes>` — simplest, no data APIs.
- **Chosen solution:** (a), importing from `react-router` (the v7 package; `react-router-dom` is no longer needed).
- **Reasoning:** SPA on Vercel matches CLAUDE.md; data mode gives layout routes for `RequireAuth` without adopting a framework. Data fetching stays in TanStack Query, not loaders, to keep one server-state tool. Accepted tradeoff: loaders/actions unused for now.

### ADR-13: Formik validation via in-house Zod adapter; single root ESLint flat config + Prettier

- **Problem:** (1) Formik natively expects Yup; CLAUDE.md mandates Zod. (2) OQ-003 mandates one root lint/format config serving browser (JSX) and Node code, runnable per app via `--filter`.
- **Options considered:** (1a) add Yup — second validation library; (1b) `zod-formik-adapter` — extra dependency with Zod-major compatibility lag; (1c) 15-line `toFormikValidate(schema)` in `lib/formikZod.js` mapping `issues[].path` to Formik's nested error object. (2a) root `eslint.config.js` with path-scoped blocks (`apps/web/**`, `packages/ui/**` → browser globals + react-hooks + react-refresh + JSX parsing; `apps/api/**`, `packages/shared/**` → node globals; `**/*.test.{js,jsx}` → vitest context) plus `eslint-config-prettier` last, global ignores for `**/dist`, `**/coverage`, `supabase/.temp`; (2b) per-app configs extending a shared package — more files, contradicts OQ-003.
- **Chosen solution:** (1c) and (2a). Plugin set mirrors the official create-vite React template (`@eslint/js`, `globals`, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`), including its `no-unused-vars` `varsIgnorePattern: '^[A-Z_]'` so JSX-only component references are not flagged. ESLint and plugins are root devDependencies; each app also lists `eslint` and `prettier` (via `catalog:`) so `pnpm --filter <app> lint` resolves the binary locally.
- **Reasoning:** Keeps one validation library; avoids a dependency whose Zod v4 support is uncertain. Path-scoped flat config is exactly what OQ-003 asked for, and mirroring create-vite minimises plugin/ESLint-major incompatibilities. Accepted tradeoff: a new app outside `apps/web`/`apps/api` needs a glob added to the root config (it does not inherit runtime-specific rules automatically — only the base rules).

### ADR-14: Test harness — Vitest in run mode, jsdom for web, node + Supertest for api

- **Problem:** FR-018/019/022 require suites that run from root and exit.
- **Options considered:** (a) Vitest per app with `test` = `vitest run`, web config inside `vite.config.js` (`test.environment: 'jsdom'`, `setupFiles`), api `vitest.config.js` (`environment: 'node'`); root `pnpm -r --if-present test`; (b) a Vitest workspace/projects file at root — one process, but couples the apps' configs and bypasses per-app `--filter` scripts the spec names; (c) happy-dom instead of jsdom — faster, slightly less complete DOM.
- **Chosen solution:** (a) with jsdom.
- **Reasoning:** `vitest` without `run` enters watch mode in a TTY and would hang `pnpm test` (FR-022). Per-app configs match the spec's per-app commands exactly. jsdom is the RTL default with fewest surprises. Tests never call real Supabase or AI APIs: fake `authService` is injected; AI SDK clients are mocked. Accepted tradeoff: two Vitest processes (negligible at scaffold size).

### ADR-15: Supabase CLI as a root devDependency; Docker required for local stack

- **Problem:** FR-021 requires `supabase db push` against a local instance; the CLI and a local Postgres/Auth stack are infrastructure dependencies.
- **Options considered:** (a) `supabase` npm package as root devDependency, run via root scripts, Docker Desktop for `supabase start`; (b) require a global CLI install (scoop/brew) — version drift between teammates; (c) no local stack, point every developer at a hosted dev project — no Docker, but shared mutable state and FR-021 wants local.
- **Chosen solution:** (a); (c) documented as a fallback for machines without Docker.
- **Reasoning:** Lockfile-pinned CLI version for everyone; `pnpm db:start` is one command. Accepted tradeoffs: Docker Desktop (WSL2 on Windows) is a prerequisite, and the package's postinstall must be allowed via `allowBuilds` (ADR-1). With zero migrations, `supabase db push --local` succeeding means "nothing to push"; the task verifying FR-021 applies and reverts a throwaway migration to prove the path.

### ADR-16: Logging — pino + pino-http with redaction; pino-pretty dev-only

- **Problem:** FR-003 requires each request logged as structured JSON; CLAUDE.md requires AI event logging without secrets.
- **Options considered:** (a) pino + pino-http middleware (request id, latency, status auto-captured) and a child logger per request; (b) hand-written `res.on('finish')` logger — reinvents pino-http; (c) morgan + pino — two loggers, morgan isn't JSON by default.
- **Chosen solution:** (a). `utils/logger.js` creates the base logger with `level: config.logLevel` and `redact: ['req.headers.authorization', 'req.headers.cookie', '*.apiKey', '*.serviceRoleKey']`. `genReqId` honours an incoming `x-request-id` or uses `crypto.randomUUID()`. `start` emits raw JSON (what FR-003 checks); `dev` pipes to `pino-pretty` for readability. Test env sets level `silent`.
- **Reasoning:** pino-http is the canonical pino integration and keeps request logging to one line of setup. Accepted tradeoff: one extra small dependency; pretty output only in `dev`.
